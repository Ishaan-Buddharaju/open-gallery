## Architecture Considerations

### Email & Image Data Flow Options

#### Upload Considerations

1. Telegram bot
2. SMS via provider
3. captive portal with presence-as-authentication (hostapd + dnsmasq DNS interception)
4. AirDrop via opendrop onto the raspi
5. NFC tag to PWA to PWA Web Share Target
6. Rotating HMAC-signed QR projected on the wall

Design considerations: Ease of use, Speed, and Reliability are key above engineering complexity. *Recall Larry Tesler's Law (irreducible complexity), easy is hard*

From this lens, I ruled out Telegram for requiring extra app for users, airdrop for often being unreliable, and nfc for requiring access to the physical tag. SMS, Email, and QR are 3 channels that support 2 use cases for different groups.

Final Modes: 
* QR/Web is great if you're looking at the wall/invited people (thus web -> wall time should be ~10 seconds).  
* SMS lets you easily share a number, and people are used to texting numbers. It's a convenient alternate to scanning the QR, but I must manage the bot, ask the right questions to get metadata on the images.
* Email has the same convenience as SMS for being on location or not, but helps laptop users (if you don't want to send them to the webpage), and let's me share to demographics who may keep images on computers or prefer email to text. 

#### Image Flow Application Design Considerations

Considered following design patterns from image injest -> moderation -> display
1. Injest Goroutine -> Python moderation service via in socket bytes -> moderation decision -> writing image shared on device resource -> go display loop
* Con Adds mem copy to send image via bytes
* Pro prevents writing unmoderated content to the shared resourse first
* Con adds socket image time & processing complexity to translate bytes to img object within python servcice
* Con requires some interrupt or signal from python to go service rather than putting the image on the display routines channel
* Pro seperates injestion logic & credentials to go and enables normalization from many (3 injestion channels) to one structure

2. Injest Goroutine -> Python moderation service via shared resource -> moderation decision -> rename/delete img on shared resource -> rename causes consumption by the go display loop w/o interfacing with injestion or moderation

3. Injest Goroutine sends img location (gmail, sms, or web) -> python moderation service (grabs img directly from source) -> moderation decision -> injestion goroutine -> writes img from source to shared resource -> display loop takes from resource w/o interfacing with injestion or moderation

4. Injest within python moderation service -> moderation decision -> python writes to shared resource -> display loop injests img from shared resource
* Con adds injestion normalization step to the python runtime (slower & more memory inefficient)
* Pro removes handoff from go -> python, removing in mem

### Webhooks vs Polling Gmail
* TLDR use webhooks for this (how often are emails vs just getting the gmail push)

Polling would require a separate thread polling the gmail api at regular intervals, while webhooks would be triggered by the gmail server when a new message is received. Gmail webhooks are more efficient given the cadence but require the extra workflow described in the cursor tracking section. Polling would also require logic to diff the messages on each get request to determine which messages are new since there isn't an inate new message endpoint. The suggested Gmail flow is what I implemented here. 

### Gmail History Cursor Tracking

The gmail pub/sub usage requires the following flow: 
```gmail notification via subscription (with new history id) -> gmail api call message history with new_messages filter -> iterate over message ids in respnse -> get message by id & get message attatchemnts by id calls```

The history id represents the point in gmail pagination history to start and show the new messages, thus I need to track the prior id and call the gmail api with the `history_id` from before the subscription notificationto get the new messages. Calling with the `history_id` from before the subscription notification will return no messages since that is the current point with no new messages.

I opted to add the sqlite database with the sqlite driver in pure go to track the id durably across restarts while maintaining the cross compatibility of the runtime. Using sqlite3 in cgo would destroy this.
* The added complexity required reduced throughput the id necessitates atomic history operations to avoid race conditions in the db and duplication of messages being processed across different histories. 
* Tradeoff is acceptable since trying to process more than one new email at a time runs into the memory limitations anyway.
